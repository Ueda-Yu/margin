# Margin — Operating Rules for Change Units, Merging, and the Improvement Cycle

| Item | Value |
|---|---|
| Policy ID / first version | `margin-change-policy/v1.0` |
| Scope | A single private repo, one owner, three Bot lines: features, QA, and usability/performance |
| Effective point | The SHA of `main` that adopts this document. The figures below are initial settings, not track records |
| Priority order for decisions | Do not lose records → Do not obstruct input → Make it searchable → Encourage re-reading |
| Units of judgment | A **request** is a demand that has arisen, a **promise** is a result whose pass/fail can be shown independently, and a **CL** is a single PR. The three are tracked under separate IDs |

**Basic rule: the implementation, tests, and evidence for the same promise go into one CL; do not mix in a different promise.** What CL reduction targets is duplicate PRs and integration waiting, not the number of tests. Merging into `main`, deploying to the owner's PC, and confirming demand in actual use are each separate judgments.

## 1. Intake and Change Units

Place the request ledger in `docs/requests.yml` and the classification rules in `policy/change-rules.yml`. If something is unimplemented at intake, its ledger state is `proposed`, and it does not count as a completed result.

| Condition | Consequence |
|---|---|
| A demand arrives | Issue a `request_id`, source, reference, summary of the demand, expected result, and the acceptance condition IDs for the target. When transcribing from a reading log, record only the event (e.g. "deferred due to cross-device transcription"), not the body text or the source itself |
| There is an unmerged PR for the same acceptance condition ID and the same expected result | Link the new request ID to the existing PR. Put QA failure cases, measurement instruments, and reproduction procedures on that branch too; do not open per-Bot PRs |
| Even if only one side is merged without prerequisites, it can deliver an acceptance result separate from the other | Give it a separate `promise_id`. Example: "can be read under the same ID after a restart" and "can be restored to a different directory" are separate promises |
| A single result cannot be shown unless the UI, DB, and tests are all in place together | Put them under the same `promise_id` and the same PR. Do not merge layer by layer in advance |
| Maintenance that does not change behavior toward the user | Make the promise a verifiable result from the maintainer's viewpoint, e.g. "restoration from the same fixed sample can be reproduced with one command." If it is only "tidying up," it cannot be started |
| Changes the schema, a migration, a fixed sample, or expected values | Only one responsibility PR may be open across the whole repo at a time. Acquire `contract-lock` before starting, and release it on merge or withdrawal. Other Bots either commit to the responsibility PR or proceed to independent work that does not change the contract |
| There are 3 implementation slots in progress, or prior work exists on a file scheduled to change | Do not start new work; support the testing, reproduction, and measurement of the preceding PR. Allocate free slots in the order "data preservation failure → save/restore → input → search/migration → other"; within the same rank, in ascending intake number order |

### Size Judgment

Let `L` be the **added lines + deleted lines** from the merge-base with `main` to the PR head, and `F` the number of changed files. Tests, handwritten samples, and documents are included. Only generated artifacts and lockfiles that are on the allowlist and can be fully regenerated by a verification command are excluded from `L, F`; the pre-exclusion values and the regeneration result are also recorded. A binary that cannot be measured blocks the PR unless its match can be verified from its generation source.

| Condition (apply from the top, first match) | Judgment and action |
|---|---|
| The number of promises is 0, or 2 or more | Return to intake regardless of size. If multiple test cases show the normal and abnormal paths of the same promise, that counts as 1 |
| `L > 400` or `F > 12` or planned effort `E > 480 min` | **Large CL.** Cannot be merged normally. If there is an independently verifiable intermediate result, split it and record the parent request and dependency order |
| A large CL where splitting would leave inconsistencies among the migration, the read/write implementation, and compatibility samples in `main` | A candidate for `atomic-contract`, for this contract change only. Send it to the owner-confirmation lane only if there is a reproduction test showing the inconsistency, the migration/restoration/round-trip results from the old version are all in place, and all of `L ≤ 800, F ≤ 24, E ≤ 960 min` are satisfied. Otherwise return it to design |
| Not large, and all of `L ≤ 120, F ≤ 5, E ≤ 120 min` are satisfied | `small` |
| Any other CL that is not large | `standard` |

## 2. PR Attributes and Estimates

Place the following in the machine-readable fields of the PR body. Paths, line counts, timestamps, and execution results are obtained from CI or repo events and cannot be overwritten by hand into a lighter classification. Path judgment applies to both before and after a move.

| Attribute | How the value is determined |
|---|---|
| `request_ids / primary_request` | List all linked requests. The primary request is the intake number that first gave rise to the promise. This avoids double-counting effort from later requests |
| `source / kind / summary / ref` | For each request, one value each: source = `plan / roadmap / owner-use / QA / perf / incident / maintenance`, kind = `feature / defect / recovery / measurement / upkeep`. The summary is "the event that triggered it → the expected result," and the reference is one of a section, an Issue, a failed run, or an anonymized observation ID. The source is determined by the first evidence, not by who filed it |
| `promise_id / acceptance_ids` | One promise, and one or more test or manual-judgment IDs that verify it. The correspondence table also registers the contract to be protected and the required tests |
| `area` | `core` if it touches `lib/db/**`, `lib/schema.sql`, `lib/transfer/**`, `tests/fixtures/**`, the merge rules or CI definitions, or a contract ID for persistent IDs, save finalization, recovery, migration, search index rebuild, or the localhost boundary. Otherwise, `extension` if it only touches registered UI, optional reviews, measurement instruments, explanatory text, etc. If both, `core` with `mixed=true`. Unregistered paths and contracts are stopped until the classification table is updated |
| `owner_gate` | `true` if it involves the meaning of data, target devices, external transmission, irreversible operations, changes to policy/gate definitions, acceptance on the owner's PC, or `atomic-contract`. It is the logical OR of the flags of the relevant request and contract IDs. Out-of-scope items such as cloud sync do not become startable by owner confirmation alone; a scope revision is required first |
| `E / effort_band` | The planned total work minutes from the formula below. `S: ≤120`, `M: 121–240`, `L: 241–480`, `XL: >480`. Waiting time is not included |
| `deps / actor / lock / policy` | Dependent PR numbers, the assignee of each task, the responsibility PR number, and the version and SHA of the applicable policy |
| `evidence` | Candidate SHA, fictional sample ID, reproduction command, expected values and measured values, CI run, unverified items. Values before execution are `not-run` |

**Effort model (v1.0)**: `E = 30 + 30P + 30A + 90C + 60H` minutes. `P` is the number of distinct registered areas changed (UI / DB / transfer / samples / automated tests / scripts / documents / CI & policy), `A` is the number of mandatory acceptance cases registered for the promise, `C` is whether a contract lock is required, and `H` is whether owner confirmation is required (each 0/1). When using the atomic exception, re-judge the cap with `H=1`. At start, calculate with the planned paths; when the diff is finalized, recalculate with the union of the planned and actual areas. Keep the initial value as well, and use it to verify estimation error.

## 3. Merge Judgment and Standard Lead Times

Lead time is the **calendar time** from acquiring a start slot to merging. Nights, waiting for the owner, and CI retries are included; the clock does not stop. In the table below, apply the first matching row from the top. The standard time is a forecast, not an automatic approval deadline.

| Condition | Earliest merge point | Standard time at start |
|---|---:|
| Any of: a required attribute is missing, the request is out of scope, a size violation, an unmerged dependency, another PR is using the lock, a required test has not passed | **Stop.** Re-judge after the cause is resolved. State the outlook as `blocked` together with the original lane forecast | Cannot be determined |
| `owner_gate=true` | After the common gate and per-target verification, when the owner has recorded the candidate SHA and the confirmation result | `B + 24h` |
| `area=core`, or `source` includes `incident` | When the applicable tests among the per-contract regression tests and the incident reproduction test have passed, after the common gate | `B + 8h` |
| `extension` and `small`, and it changes only document display / explanatory text without changing execution paths, recovery procedures, contracts, or expected values | **Immediate** = automatic merge right after the common gate succeeds. No waiting for periodic review | `B` |
| All other cases | Automatic merge after the common gate and the success of the integration / UI / measurement tests corresponding to the acceptance IDs | `B + 4h` |

`B` is `S=4h / M=12h / L=24h / XL=48h`. To avoid dependency waiting, work that has unstarted and unmerged prerequisites is not put into a start slot. There is one owner-confirmation slot, ordered by verification completion time, and by PR number if simultaneous. At start, if there are `q` preceding items waiting for owner confirmation, add `24h × q` to the forecast, and save the initial forecast and the latest forecast separately.

- **Common gate**: Against the integration result of the candidate and the latest `main`, if the attribute check, the size check, the already-introduced required CI (lint, types, unit, migration, round-trip, Playwright), and the evidence check for the corresponding promise all succeed, the PR enters the queue. A missing or cancelled required run is not a success. Tests not yet introduced in the initial build are reported as not introduced, and a promise that needs such a test is not passed.
- **Correspondence of verification**: For saving, the same ID after a restart and the unsaved indication on failure; for recovery, restoration to a different directory and comparison with the canonical copy; for migration, success from the old version, halt on failure, and round-trip; for search, the fixed expected IDs and the match before and after an index rebuild — pulled from the contract ID of the change target. For performance delivery judgment, use the production build on the owner's PC, 10,000 records, 30 runs each, p95 ≤ 500ms; for 100,000 records, judge by backward browsing, search interruption, and preservation of the completed export.
- **Order and expiry**: Merges are serial. If the candidate SHA or the integration target changes, re-run the verification of the integration result; do not reuse confirmations for the old candidate. A gate-changing PR is approved by the owner under the old rules on the `main` side, and does not pass under rules it loosened itself.
- **First application example**: "Register a fictional book and read it under the same ID even after a restart" is one promise even if it spans UI, DB, and tests. If it includes a migration and samples, the responsibility PR is this one PR, and it is `core`. If it does not change the meaning of adopted data, it takes the post-verification lane. Even after merging, if recovery is unverified, the demo is for fictional data only, and the owner's real data must not be loaded.

## 4. Monitoring and Intervention

Recompute the judgment at each event: PR creation, update, CI completion, confirmation, merge, withdrawal. Times are UTC. Tie the required check `change-policy` and the merge queue to the protected branch, and do not allow direct pushes. Until automation is introduced, the owner records the judgment result by name using the same table, and automatic merging is disabled.

| Observation condition | Automatic recording / consequence |
|---|---|
| Start, verification submission, CI start/end, owner confirmation request/response, merge or withdrawal | Append to the ledger: event time, PR / request / promise IDs, version, lane, size, forecast, stop reason. Work ended midway also remains in the effort tally |
| End of a work session | Record, per assignee, `implementation / QA / measurement / rework / operations` and the activity minutes. Owner minutes, per-Bot operating minutes, CI runner minutes, and calendar time go in separate columns. Do not add parallel operating minutes together and call the sum elapsed time |
| 80% of the initial lead-time forecast reached and still unmerged | Post the remaining gates, what it is waiting on, and the latest forecast on the PR, once. If it exceeds 100%, mark it `late`, and the assignee prioritizes clearing the blockage over new starts |
| Actual work minutes (owner + Bots) exceed `1.5 × initial E` | `estimate-miss`. Record the unmet acceptance cases and re-judge the size and the number of promises. Do not omit tests merely because of the overrun |
| The same candidate and the same required test fail twice | Stop automatic retries and assign the failure case to QA. Resume when there is new fix work or evidence that the test infrastructure has been restored |
| Even one detection of data loss, mismatch with the canonical copy, or continued writing while corrupted | Stop normal merges and real-data loading, and issue an incident request. Preserve the suspect DB without replacing it. Verify only the repair candidate, and lift the stop after a pass on restoration to a different directory and comparison with the canonical copy, plus owner confirmation |
| There are new records but no latest-state verified external copy | Separately from mergeability, stop upgrades and bulk imports on the owner's PC. Lift after the copy is verified |
| A revert, reopening, or regression incident within 14 days of merging | Cross-link the causing PR and the fix request, and update the result to `rework`. Before 14 days have passed, the state is `observing`, not "no regression" |

Evidence kept in the repo is limited to fictional-sample results with the target SHA, and aggregates. If evidence would include the owner's DB, WAL, backups, actual quotations, usage logs, or personal paths, refuse to register it as evidence and replace it with an anonymous ID in a local record.

## 5. Feedback of Resources and Results

At the effective point, take a one-time inventory of existing commits, PRs, and CI history. Past planning commits are `planning`, results with no executed tests are `unverified`, and values with no effort log are `unknown`. Do not treat commit intervals as effort, and show the number of missing measurements together with the denominator.

| Point in time / condition | Output and judgment |
|---|---|
| Every Monday 00:00 UTC | Close the preceding 7 days and generate a weekly report with **data-loss risks and unverified items first**. By `area × source × lane`, list the numbers received, completed, and withdrawn; the number of completed promises; CLs per promise; owner minutes, Bot minutes, CI minutes; rework minutes; calendar time p50/p90; owner waiting time; the number of deadline overruns; and the number of regressions observed over 14 days. If completions are zero, ratios are `N/A`; incomplete items list their current dwell time separately |
| Multiple PRs arise for the same promise | Classify each additional PR as `size-split / independent-prerequisite / duplicate / regression`. If there is even one `duplicate`, add a duplicate search over promise IDs to the regression tests at the following week's intake. Necessary splits are not included in the reduction target |
| Policy review every 4 weeks | Compare the completed group of the preceding 28 days by lane and effort band. If the count is under 10, change no figures and carry over to the next review. A quantile is the `ceil(p × n)`-th value in ascending order. Show the number of exclusions due to missing measurements, and if the missing rate for that metric exceeds 10%, fix the recording path before calibration |
| Twice in a row in the same group, the actual p90 exceeds 125% of the standard time | Compare waiting time across CI waiting, owner waiting, and dependency waiting. If the largest item is CI, make duplicate-run consolidation the next maintenance request; if it is the owner, an inspection of the order of submission to the waiting slot; if it is dependencies, a pre-start inspection. If tied, use the order listed. If it still exceeds in the next 28 days, propose revising that group's standard time upward to the most recent p90 rounded up to the hour unit |
| At the 4-week review, by effort band, the median of `actual work minutes / initial E` is `>1.5` or `<0.67` twice in a row (at least 10 items each time) | In the next-version candidate, multiply that band's effort by the median and round up to 15-minute units. Band selection is from before the correction; size and lane judgment are from after the correction. Recalculate past PRs and proceed to the trial conditions below |
| Weekends of Weeks 5–8 | Locally tally actual-use save opportunities, reasons for deferral, natural re-references, and the number of cases where the source was useful. Exclude test searches. Separate old notes from new records, and distinguish zero opportunities from recording omissions. If there are 2 deferrals due to transcription, route them to an owner-confirmation request about the device path, not to UI polish |
| Week 8 → Month 3 → Month 6 | If there is no natural reference opportunity at Week 8, do not expand until Month 3, treating demand as "unverified." If there is still no opportunity at Month 3, freeze new features and external expansion; if only the old notes are useful, move to archive maintenance. At Month 6, if use is by the owner only, keep solo maintenance; only if another person was able to re-reference unaided, make the next single seat under the same conditions a candidate |

## 6. Policy Versions and Termination Conditions

| Condition | Policy state transition |
|---|---|
| There are multiple revision candidates at the 4-week review | Put only one into the next policy PR, in the order: safety defects → recording gaps → waiting time → effort calibration. Attach the reason for the change, the target group, the old value, the new value, and the re-judgment difference over the most recent 28 days |
| A change to a figure or a classification rule is approved | Raise the minor version, and save the old version and the SHA at which application begins. Trial it for 28 days on newly started work only. Only a strengthening of a safety stop rule applies immediately, including to open PRs |
| Trial end | Adopt it if the target group has at least 10 items each under the old and new rules, the target metric (waiting p90 for waiting time; the median of `abs(actual/estimate − 1)` for effort) has decreased, the 14-day-observed regression rate has not increased, and the target group's owner work minutes per completed promise have not increased. Hold the judgment until the 14-day observation of the final PR ends. If the count is insufficient, extend by 28 days only; if still insufficient, or the conditions are not met, revert to the old version. A preservation failure stops the trial without waiting for its end |
| End of Week 4, end of Week 8, Month 3, Month 6 | Separately from periodic calibration, the owner confirms the premises of single-user, local operation, and the Bot configuration. If any of public operation, multiple writing principals, or delegation of approval to someone other than the owner is decided, do not stretch the current version for expanded use; stop the relevant changes until the next major version, which defines authority and recovery responsibility, takes effect |
| No incomplete requests and no open PRs, and no starts for 56 days | Set the state to `maintenance`, and suspend empty weekly reports and numerical calibration. While in use, continue backup checks and monthly restoration to a different directory. On the next start, resume if the current version, the protection settings, and the latest restoration result can be confirmed |
| The repo is made read-only, and the final verified external backup, readable Markdown, and different-directory restoration result are all in place | Set the state to `retired`, and end PR monitoring and the improvement cycle. Do not delete versions, judgment history, or the final SHA. On resumption, record a new effective point, and do not mix the suspension period into lead-time records |
