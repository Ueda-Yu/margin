# Margin — 工程・変更コスト・価値の計測規程

| 項目 | 定義 |
|---|---|
| 方針ID | `margin-measurement-value/v1.0` |
| 親方針 | `margin-change-policy/v1.0`（以下「変更規程」）。受付・着手・停止・マージ・方針改訂の正本とする |
| 発効点 | 本文書を採用した `main` のSHA。予測には方針ID・発効SHA・予測時刻を付ける |
| 適用範囲 | 非公開の単一repo、本人のローカル単席版。外部テストは成果物又は独立した単席に限る |
| 数値の位置付け | **本書の数値はすべて実績ではなく初期設定**（元計画の条件、初期係数、観測窓、判定例を含む）。計画を実装・利用・販売の証拠としない |

| 判定の単位 | 要求の発生＝`request_id`、独立して合否を示せる結果＝`promise_id`、PR＝`cl_id`。`merged`、本人PCでの `deployed`、自然な用途での `used` は別イベント |

## 1. 二案の仕様・要件台帳

### 1.1 読み方と既存契約への接続

以下の `P` は `PLAN.md`、`R` は `ROADMAP.en.md`。`Wn` は対応する Week 節、`予定` は “Deployment and decision schedule”、`破綻` は “What would break the plan”、`経路` は “Where it could spread” を指す。台帳IDは行の参照キーであって、契約ID・受け入れ条件ID・実装済み約束IDではない。

| 略記（新規の契約IDではない） | 引く先：変更規程 §2–3 の契約・受け入れ条件 |
|---|---|
| 永続／保存 | 不変ID・再起動後の同一ID／保存確定・失敗時未保存 |
| 復旧／移行 | 別ディレクトリ復元・正本比較／旧版移行・失敗停止・往復 |
| 検索／境界 | 固定期待ID・索引再構築前後一致／localhost限定 |
| 負荷／共通 | 本人PCでの性能・縮退判定／属性・サイズ・必須CI・約束の証拠 |
| 本人／運用 | 本人確認対象・候補SHA／変更規程 §4–6 の監視・判断・終了条件 |

各表の「約束候補」は結果名。「検証」は `acceptance_ref` であり、出所の節内の条件を下表の試験内容で特定する。上表の略記があればその既存契約にも結ぶ。資料中にリテラルのIDがないため、架空の既存IDを作らない。着手前に `policy/change-rules.yml` の対応表から実IDを解決する。既登録ならそれを再利用し、未登録の独立した判定だけ原文の節・条件を根拠に受け入れIDを登録する。未解決・多義なら停止。以下の集合行は計画上の索引であり、独立した結果を同じPRに束ねる理由にはしない。

## 2. 工程と実作業分

### 2.1 二軸分類

`work_class` は**何のための時間か**、`activity` は**何をしていた時間か**。セッションを目的又は活動の切替時に分け、各行は各軸で一値だけを持つ。

| work_class | 判定 | activity（変更規程 §4） |
|---|---|---|
| 管理 `manage` | 受付・分類・見積もり・レビュー調整・週報・方針改訂 | 通常 `運用`、集計は `計測`、規則検証は `QA` |
| 実装 `deliver` | 新規の約束を初めて成立させる。保守担当向けの新しい検証可能な結果を含む | 構築 `実装`、初回検証 `QA`、測定 `計測`、初回配備・訓練 `運用` |
| 修正 `repair` | 既知の欠陥・回帰、失敗後の作り直し・再検証 | 修復・やり直し `手戻り`、原因再現・再検証 `QA`、再計測 `計測`、復旧操作 `運用` |

定期点検の遂行は管理／運用、新たな点検手段の納入は実装、点検不合格の解消は修正。同じ失敗を契機とする修正でも受付調整だけは管理。`rework_flag` は既に行った作業をやり直す区間（再検証を含む）に付ける。`repair` の全分と手戻り分を同義にしない。

### 2.2 記録契約

| ファイル | キーと必須フィールド |
|---|---|
| `docs/specs.yml` / `docs/requirements.yml` | `id, revision, source_section, statement, promise_candidates[], acceptance_refs[], resolved_acceptance_ids[], contract_ids[], related_ids[], status, supersedes`。REQは `actor, occasion, purpose` も保持。削除は廃止版として残す |
| `docs/requests.yml` | 変更規程 §1–2 の全属性に `spec_refs[], req_refs[], change_type, impact_ref, promise_ids[], primary_request, status` を追加。複数要求でも約束・実分を複製しない |
| `docs/metrics.yml` | `promises`（約束・主要求・受け入れID・CL履歴）、`events`, `sessions`, `runs`, `forecasts`, `impacts`, `windows`, `decisions`。各行に一意キー・UTC・方針版・対象参照。訂正は `corrects_id` で追記 |
| `docs/evidence/` | 対象SHA、架空試料、再現コマンド、期待値・実測値、run ID、未検証事項。実行前に成功欄を埋めない |
| repo外のローカル記録 | 本人環境の詳細・利用日誌・配備確認。repoへは匿名観測IDと集計のみ。DB・WAL・引用・個人パス等を検出した証拠は拒否 |

`events` の共通列＝`event_id, stage, event_type, at_utc, actor, request_id, promise_id?, cl_id?, candidate_sha?, base_sha?, lane?, block_reason?, session_ids[], run_ids[], artifact_ref, policy_sha`。`actor` は `owner / bot-feature / bot-qa / bot-ux-perf / CI`。未発番参照はnull＋理由。イベント自体は時間を消費したという証拠ではない。

| 工程 | イベント・時刻 | 主な担当 | 作業分の参照／成果物 |
|---|---|---|---|
| 受付 | `received` 到着時 | 本人・各Bot | 管理session／要求・匿名事象 |
| 分類 | `classified, linked, blocked` 判定時 | 各Bot・本人 | 管理／主要求・契約・area・source・重複先 |
| 見積もり | `estimated, reestimated` 各算定時 | 担当Bot・CI | 管理／P,A,C,H、初回値・最新版・影響集合 |
| 着手 | `slot_acquired, lock_acquired, work_started` 各取得・開始時 | 本人・各Bot | session／着手枠・責任PR・予定パス |
| 検証 | `submitted, ci_start, ci_end, failed, resubmitted` | QA・操作性／性能Bot・CI | QA・計測等のsessionとrunner分／試料・候補・結果 |
| 確認 | `approval_requested, approved, rejected, invalidated` | 本人・CI | 管理又は検収session／対象SHA・確認結果。不要なら `not-required` |
| マージ | `queued, merged, withdrawn, lock_released` | CI・本人 | 管理session又はrun／統合SHA・結果・解放記録 |
| 観測 | `observing, regression, reopened, reverted, observation_closed` 発生時・マージ後14日満了時 | QA・本人・CI | 修正は原因PRにリンク／未満は `observing` |
| 週報／較正 | `week_closed, reviewed, change_proposed, trial_closed` 締め・判断時 | 計測Bot・本人 | 管理／対象窓・分母・予測誤差・採否 |

`sessions`＝`id, actor, start_utc, end_utc, pauses_min, active_min, work_class, activity, rework_flag, stage, primary_request?, promise_id?, impact_slice?, artifact_ref, missing_reason?`。セッション終了時に本人はタイマー、Botはジョブの作業区間から休止・キュー待ちを除いて分換算する。同一担当の重複区間は解消するまで欠測。週境界で切り分け、丸めは集計表示時のみ。CIは `runs` に runner ごとの開始・終了・状態を記録し、Bot分には入れない。週報等の共通費は `shared` として週に一度だけ計上。撤回・失敗runも消費に含む。**コミット間隔、PRの開放時間、確認待ちは作業分ではない。** 欠測は `unknown`、未導入は `not-instrumented`、確認済み無稼働のみ0。欠測件数／期待レコード数を添え、合計は既知分の下限として表示する。

### 2.3 工数予測（分）

CL判定用は変更規程の `E=30+30P+30A+90C+60H` のまま。`P` は登録済み変更領域の異なり数、`A` は必須ケース数、`C,H` は契約ロック・本人確認の指示変数。原子例外は `H=1`。差分確定時の `P` は予定と実測の和集合。次式は予算配分用であり、サイズ上限を回避する式ではない。

```text
M = 15 + 5P + 5A + 30C + 20H
D = E − M
管理予測 = M
実装予測 = (1−f)D
修正予測 = fD + 15J + 10K
```

`f=1` は既知の不具合・回帰解消を主結果とするCL、それ以外は0。`J` は既知の失敗再現ケース数、`K` は既に実施済みで追加再実行が必要なケース数（初回必須実行を除く）。不明なら0を仮定せず未見積もりとする。新規CLで後から失敗したら初回予測を残して更新する。PR外の共通管理は受付のみ5分／件、週報30分／回、4週レビュー60分／回の予定枠。PRに移った受付分は `M` の内数に振り替える。実績は式で配賦せずsessionから求める。

## 3. 運営・整備への拡大と要件再定義

| 範囲 | 追加・更新するSPEC／REQの境界 | 起点→ `source / kind` の例 |
|---|---|---|
| 運営 | SPEC-001,006–008,020の配備・外部コピー鮮度・復元証拠、REQ-008–013の利用観測・異常停止。担当・時計・解除試験のない「監視強化」は約束にしない | 計画済み配備 `roadmap/feature`、利用見送り `owner-use/measurement`、実損傷 `incident/recovery` |
| 整備 | 依存更新で同一試料を再現、旧版移行・巻戻し、計測器の欠測検知、規則再判定の再現性を対象とする。受け入れ結果のない整理は対象外 | 定期更新 `maintenance/upkeep`、失敗run `QA/defect`、負荷超過 `perf/measurement`、計画起点 `plan/feature` |

`source` は最初の証拠で固定する。`maintenance`（出所）と `maintenance`（repoの休止状態）は別。`expand` は新たな検証義務を加える差分、`redefine` は既存の対象者・機会・目的・合否境界を置き換える差分。既定条件の不合格を元の意味のまま直すだけならどちらでもない。

### 3.1 差分予算

差分ごとに採否前の基準SHAと提案版を固定し、変更IDから正逆の明示リンクを辿り、意味・合否・運用手順が変わる対象一覧をレビューする。単なる参照だけの項目は理由付きで除外。承認した一覧をソート・重複除去して次式に入れる。

| 変数 | 決定単位 |
|---|---|
| `s,r,p,t` | 追加・改訂・廃止の影響を受けるSPEC、REQ、約束、試験IDの各異なり数。旧新の同一IDは1件 |
| `v` | 再検証すべき `(試験ID, 対象環境, 版経路)` の異なり数 |
| `m,d,h` | 移行経路 `(旧形式,新形式)` 数、改訂する運用・説明文書パス数、本人確認の独立した判断事項ID数 |
| `i` | 影響分析票数（同一基準SHA・同一意味差分で1票）。単なるPR分割で増やさない |

```text
C_expand   = 20i + 10s +  5r + 15p + 10t + 10v + 45m + 10d + 20h
C_redefine = 30i +  5s + 20r + 20p + 15t + 15v + 60m + 15d + 30h   [作業分]
```

`t` は試験定義の影響分析・変更、`v` は再実行であり同じ作業分を二度記録しない。混在時は意味置換と純増を差分IDに分け、同じ作業キー `(作業種,対象,環境,版経路)` は再定義側を優先して一方だけに割当。`impacts` に `delta_id, base_sha, proposed_revision, trigger, type, before, after, affected_ids, excluded_with_reason, work_keys, coefficients_version, estimate_first/latest, session_ids, actual_known_min, missing, gate, outcome` を残す。共通作業は代表差分IDに一度だけ記録する。

**`C` は当該差分の作業パッケージ予算であり、CL全体の `E` に丸ごと加算しない。** 工程予算を作る際は管理（分析・本人確認）、実装又は修正（対象改訂・試験・移行・文書・再検証）に分類し、§2.3の各分類額とその分類の差分予算合計の**大きい方**を用いる。複数CLにまたがる作業キーは責任CLにのみ配分。実分は同一sessionをクラス別・差分別に別の切り口で見る。

### 3.2 通過条件と集計

- 両変更とも変更規程 §1–3 のサイズ・着手枠・パス登録・依存・試験・レーン判定を通常どおり受ける。契約にかかるパス又は契約IDは `core`、混在は `core,mixed=true`。スキーマ・migration・固定試料・期待値変更は着手前に唯一の `contract-lock` を取得する。
- 意味・端末・外部送信・不可逆操作・方針／ゲート・本人PC検収・`atomic-contract` は `owner_gate=true`。対象外の拡大は先にスコープ改訂。公開運用・複数書込主体・承認委譲なら次major版までは停止。要件の文言変更だけで保護条件を解除しない。
- 停止条件→本人確認→core又はincident→smallな表示説明のみ即時→その他の順。復旧手順変更は即時レーンでない。本人が新規則をその規則自身で承認することは禁止。
- 週報では `type × area × source × lane` ごとに差分件数、予定・実分、再検証・移行・本人待ち、撤回、欠測を出す。4週レビューは完了群で `実分/初回C` の中央値と14日観測済み回帰を比較する。複数出所は主要求で一度計上し、レーン判定には全要求を使う。

## 4. 資源・価値と判断

### 4.1 資源消費 `R`

異なる資源を比較する**予算点**であり、金額でも総実労働時間でもない。

```text
R = O + 0.25 B + 0.10 I + 0.02 T + 0.50 W
O:本人活動分  B:全Bot活動分  I:CI runner分
T:着手枠取得からマージ又は撤回までの暦分（未完了は締め時点で打切り）
W:rework_flagの本人＋Bot分（O,Bの内数への追加ペナルティ）
```

約束単位の `T` はその約束の各CL区間の和集合長。週単位は週と交差する全着手区間の和集合長を使う（並行時間を二重計上しない）。活動分は週内部分を合計し共通費を含める。週 `R` を約束別 `R` の単純和としない。

| 予測対象 | 入力と予測 |
|---|---|
| 約束 | §2.3・§3の分類別予算を担当予定表の割合で本人・Botに配分（未配分なら管理50%、実装・修正10%を本人、残りをBot）。CIは予定runnerジョブ当たり10分、`W` は再作業指定分（未分割の修正予算では半分）。`T` は変更規程 §3 の工数帯・レーン・本人待ち列の標準時間を分換算。複数CLは依存・枠順に予定区間を置く。これを上式に代入した値を `Rhat` とする |
| 週 | 締め時点の開始可能キューを変更規程 §1 の優先順・枠で予定表に置く。活動・CI予算は各予定区間内に均等配分し、週内部分と予定共通費を加える。本人確認は直列。同時刻は受付番号順。週内の `T` は予定区間和集合。停止で再開時刻不明なら既知分と `blocked/unknown` を出し、余力ありと判定しない |

週報は変更規程 §5 の全項目を保持する。月曜00:00 UTC締め、損失リスク・未検証を先頭に、受付・完了・撤回、CL／約束、各資源、待ち・滞留・遅延、回帰、重複PRの理由を示す。未着手・未マージの待機も別掲する。§4の80%通知・標準超過・`1.5E`・連続失敗の介入は予算点とは独立に実行する。

### 4.2 価値 `V` と予測

窓はUTCの左閉右開区間。自然な機会はアプリ操作でなく、**残したかった／文言や出典が必要になった場面**を単位とする。別手段で済ませた・見送った場面も分母。同じ場面の再試行は1件。試験・依頼されたデモ・起動回数・DL・送付数・関心表明は成功にも自然機会にも含めない。

| 記号 | 窓内の計数 |
|---|---|
| `D` | 必須試験・必要な確認後にマージされた異なる約束の初完了数。技術的価値であり、需要ではない |
| `Ns,S` | 自然な保存機会、うちMarginで原文と対象本を保存できた件数 |
| `Nl,L,Q` | 自然な参照機会、うちMarginで正しい文言を取り戻せた件数、そのうち必要な出典も十分で用途に使えた件数。新規／旧ノート別に分母から分ける。不明群も残す |
| `Xc,Xp,Xb` | CtoC受領者が自用途で成果物を再利用、BtoC読者が後日自力で再参照、BtoB担当者が反復業務で再使用した機会数。匿名席・経路・機会で重複排除。実際に試す機会数 `Nc,Np,Nb` も記録 |
| `V` | `(D, S/Ns, L/Nl, Q/L, Q/Nl, Xc/Nc, Xp/Np, Xb/Nb)`。本人利用と外部は分離。ゼロ分母は `N/A`、未記録は `unknown`。異なる価値を合算し外部需要に読み替えない |

窓末に次の同長窓を予測する。直近の完全な28日窓で、各機会数を次窓の予定機会数、各成功率を予定成功率と置き、`成功数予測＝予定機会数×予定成功率`。`D` の予測は予定表の窓内完了約束数。イベントが既知の外部テストは経路別の予定機会数を明記して置換してよいが、未観測の成功率は `unknown` のまま。予測と観測を別列にし、予測成功だけでゲートは開けない。

### 4.3 決定表

Astraは `repo_state`（active／maintenance／retired）と `investment`（続行／凍結／拡大／保守移行／終了）を別列に出す。**凍結するのは新機能・展開であり、復旧ではない。** 定例日は採用時にUTCで登録し、判定入力とした週・月の開始終了を固定する。以下を上から適用する。安全停止は全行に優先する。

| 順位・条件 | 判定／許される次の動作 |
|---|---|
| 読取専用化済み、最終SHAに対応する検証済み外部バックアップ・可読Markdown・別ディレクトリ復元結果がすべてある | **終了** `retired`。低利用や資源超過だけでは終了しない。履歴・版・最終SHA保持 |
| データ損失・正本不一致・破損時書込を1件以上検出、又は既存の停止条件に該当 | **凍結／対象操作停止**。変更規程 §3–4 の対象と解除条件を適用。外部コピー欠落だけなら本人PCの更新・一括import停止であり、無関係なマージまで停止しない |
| 未完了要求0かつ開PR 0かつ56日無着手 | **保守移行** `maintenance`。空週報・数値較正を休止。利用中の週次コピー確認・月次復元は継続。再着手は版・保護設定・最終復元結果を確認 |
| W4、W8、M3、M6で前提が公開運用・複数書込主体・承認委譲へ変化 | **該当変更を凍結**。新major発効まで単席規程を流用しない |
| W8でこれまで自然な参照機会0 | **現状続行・展開凍結**。需要未検証、アーカイブを残してM3に再判定 |
| M3でも自然な参照機会0／M3まで旧ノートのみ有用 | 前者は**凍結**、後者は**アーカイブ保守移行**。新たな適格証拠が出るまで適用。repo自体の `maintenance` とは限らない |
| M6で有用例が本人のみ、又は外部は送付・関心のみ | **単独保守移行**。CtoC再利用だけなら成果物の検証のみ継続可。席を増やさない |
| 直近28日で完全な週報4本、かつ `Ns≥3` で `S/Ns<0.5` 又は `Nl≥3` で `Q/Nl<0.5`（率条件ごとに分母を適用）、又は完全な連続2週で各 `R>480` 点 | **凍結**。保存経路／未保存・出典不足・検索漏れ／資源内訳に対応する修正だけを見積もる。直近窓で該当しなくなれば再判定 |
| W8以後。直近28日の完全週4本、`Ns≥3, S/Ns≥2/3, Nl≥2, Q/Nl≥1/2`、新規保存から後日の有用参照が1組以上、直近各週 `R≤480`、候補を含む次週 `Rhat≤480`、対象候補の `Rhat≤240`。さらに§7の経路条件を満たす | **拡大**＝対応する最小テスト1件のみ。M6以後の追加席は他者の独力再参照が同条件で1件以上必要。成果物の成功で席を増やさない |
| その他（分母不足、欠測、機会はあるが成功未検証を含む） | **続行**＝現行範囲の検証・保全のみ。追加投資は承認しない。W8等の必須記録が欠測なら「機会0」ではなく判断保留。計測経路を直す |

完全週＝予定した週次申告・活動・CI・観測入力に欠測がない週（機会ゼロの明示申告可）。実装前には価値率を要求せず、必須試験を継続する。拡大は候補ごとに判定し、複数適格なら現実の契機の早い順、同時ならCtoC→BtoC→BtoB。週予算には先行テストの支援・復旧分も含める。

### 4.4 較正

| 対象 | 発火条件（非重複28日ごと） | 次版候補 |
|---|---|---|
| 変更規程の標準時間・E | 同一群各回10件以上。標準の125%超のp90が連続2回、又は実分／初回E中央値が同方向に `>1.5` 又は `<0.67` で連続2回 | 時間は親§5の最大待ち要因を先に直し次窓も超過ならp90時間切上げ。Eは親§5の帯別乗算・15分切上げ |
| 分類別工数・差分コスト・CI予測 | 同一分類（差分は同種）で初回予測正かつ完了10件以上／窓、`median(実分/予測分)` が同方向に `>1.5` 又は `<0.67` で連続2回 | 最新中央値をその分類の予算係数に乗じ、分類合計を分単位切上げ。差分単価とクラス単価を同時変更しない |
| 価値率の予測 | 同一経路の対象機会10件以上／窓、率の実測−予測が同符号かつ絶対値0.20超で連続2回 | 次版候補では `次窓の予測率=clip(直近率＋最新の率誤差/2,0,1)`。成功の定義・自然機会分母は変えない |
| 候補資源閾値 | 予測・実測の対が各窓10件以上。予測が候補閾値以下だが実測が閾値の125%超だった比率が連続2窓で20%超 | 予備費として候補の予測許容上限を旧閾値の90%に切下げ（整数点）。週予算・保全試験・最低証拠数は緩和しない |

比率の分母0・欠測は除外件数を報告。対象指標の欠測率10%超なら記録経路を先に直す。件数不足の窓では数値変更なし、連続条件は成立しない。分位は昇順 `ceil(pn)` 番目。複数候補は親§6の安全→欠測→待ち→工数の順、その後に価値率・候補閾値の順で1件だけ提出。旧規則による本人確認、minor版、直近28日の再判定差分、新規着手だけの28日試行を必須とする。新旧各10件以上で対象誤差（率は絶対率誤差、資源閾値は超過承認比率）が減り、14日観測済み回帰率・本人分／完了約束が増えない場合のみ採用。不足は28日だけ延長、なお不足又は不成立なら戻す。最後の14日観測を待つ。

## 6. 検証のライフタイム予測

ライフタイムは「次の条件付き再検証まで、その証拠を何の判断に使えるか」。歴史的な成立例は消さないが、現行版・現用途への適用は期限又は前提変更で失効する。下表はすべて**初期予測**で、仕組み・資産が既に存在するとの記載だけでは時計を開始しない。技術資産はまず現物・版・試験の棚卸し、需要は実機会の観測から開始する。

| 形態／資産 | 検証まで（時計の起点→必要な観測） | 維持できる期間／更新 | 失効・分岐 |
|---|---|---|---|
| 本人単席 | 配備・復元検収→W5–8の自然な保存と後日の `Q新≥1` で成立例。`Q旧≥1` のみならアーカイブ例 | 最新の有用参照後28日を現用途の証拠窓とし、次の同種参照で更新 | 機会なしは頻度不明、W8→M3の分岐。端末変更・転記見送りは入力経路を再判定 |
| CtoC成果物 | 自然な会話→適切な成果物提供→受領者自身の `Xc≥1` が最初の検証点。返答期限到来は成功でない | 再利用から28日間は同種の成果物候補の根拠。次の独立利用で更新 | 利用未確認・引用条件変更・出典不足なら次用途には持ち越さない。席数の証拠にはならない |
| BtoC単体版 | 適格な1席を配備→後日の実参照で `Xp≥1`。所要期間は配備から自然な必要が生じるまで | 同条件の再参照から28日かつその版で復元可能な間 | 本人の代理操作、端末・蔵書形式変更、復旧不能で失効。M6の次席条件へ |
| BtoB単席版 | 直近業務を特定・許可・復旧担当決定→導入後、別の実業務で `Xb≥1` | 直近の業務再使用から28日、同じ許可・責任者・反復業務が続く間 | 許可撤回、担当不在、共有編集必須、業務消滅で失効。組織関心で更新しない |
| 保存機構 | 対象SHAの保存・失敗・再起動試験完了まで | 同じ保存契約・版・環境の間。リリースごとに再試験 | ID・確定点・DB位置の変更、不一致で即失効 |
| 復元機構 | 検証済みコピー→別ディレクトリ正本比較まで | 月次訓練の次回期限まで。新記録は週次で外部コピー鮮度を確認 | 訓練失敗・媒体変更・復旧点不足で該当保証失効、更新等を停止 |
| 検索機構 | 対象版で固定期待IDと再構築前後一致まで | 同じSQLite・索引・検索実装の間。各変更で再試験 | 文中語・短語漏れ、版変更で失効。試験合格は自然な参照成功でない |
| Markdown往復機構 | 全正本の空DB往復・競合・中断試験まで | 同じ形式版・対応状態集合の間 | 状態や形式追加・欠落・原文破壊で失効、旧新版の試料を再検証 |
| 蓄積ノート資産 | 実在と退避可能性をローカルで確認→旧ノートの `Q旧≥1` で実用例 | 退避・復元は月次、実用性は直近28日の自然な旧ノート利用で別々に更新 | 復元不能なら保全障害。参照なしは資産消滅でなく現在価値未検証。出典不足は検索成功でも用途不成立 |

外部への影響力は `Xc, Xp, Xb` を経路別に示す。ある経路の検証期間を別経路に転用しない。機会の頻度が未知なら「検証までの日数＝未定、次の観測＝表の必要条件」と予測する。

## 7. 情報・ノウハウの移転

持ち出す単位は検証済みの**手順・架空試料・集計**。製品のCtoC機能で読者が正当に共有する成果物と、運営者が次の事業に移す証拠を区別する。前者をそのまま後者へ収録しない。

| 種類 | 原記録→移転用の置き場 | 次の候補／適用条件 | 持ち込まないもの |
|---|---|---|---|
| 入力経路・負担 | ローカル日誌→`docs/evidence/capture/` の媒体別集計。転記とアプリ時間を分離 | BtoC・別製品：素材がPCに届く条件と端末差を説明できる | 一節、書名、個人端末名・パス、日誌原本 |
| 復元運用・更新前停止 | 私有媒体の記録→`docs/evidence/recovery/` の架空DB試験・版付き手順 | BtoC・BtoB・別製品：同じストレージ契約、復旧担当が指定済み | 本人DB・WAL・バックアップ・媒体識別情報 |
| 検索失敗分類・往復 | ローカルの事象→`tests/fixtures/` の独立した架空試料、`docs/evidence/search/` | アーカイブ・BtoC・BtoB：未保存／出典不足／検索漏れを区別し、対象版で再現 | 実検索語・引用・旧ノート・実際の出典 |
| 価値・閾値の運用 | `docs/metrics.yml`→`docs/evidence/model/` の分母付き集計・方針版 | 全経路・別製品：機会定義と資源単位が一致。異なる場合は式と計測器だけ運び、数値は未較正から開始 | 席・日時の組合せで本人を識別できる明細、個人利用の市場外挿 |
| 共有・交渉・配備 | 私有の連絡記録→`docs/evidence/pilots/` の匿名条件票、支援分・復旧責任・実再利用の有無 | CtoCは適切な共有条件、BtoCは独立端末、BtoBは保存許可・責任者のある同条件のみ | 相手の連絡先、業務資料、実際の共有ファイル、交渉履歴、支払意思の推定 |
| デモ・実装ノウハウ | 非公開repo→対象SHA付き架空デモ・再現手順・限定スナップショット | 全経路：候補版の試験結果と公開可能ファイル一覧を照合 | 実装repo全履歴の自動公開、秘密情報、未実行の「成功」証拠 |

### 移転ゲート

1. `evidence_ok`＝対象SHA・再現手順・結果・分母・未検証事項がそろい、架空試料又は再識別不能な集計だけ。外部送信は送信範囲に対する本人確認必須。匿名化できない小集団は数値を外に出さず手順だけを候補とする。
2. `route_ok`＝CtoCは実際の会話と適切に共有できる成果物、BtoCはPC素材・ローカル検索の必要・自分の端末と復元手順、BtoBは直近の反復照合・許可端末・復旧責任者・単席適合をすべて確認。別製品は持ち込む手順に対応するSPEC・REQ・対象環境・架空試料での受け入れ条件が登録済みであること。別製品にMargin利用者の需要を移さない。
3. `capacity_ok`＝§4.3の拡大行の本人価値・資源・窓・段階条件がすべて真。候補の支援・配備・再検証コストを次週予測に含む。初回の外部テストにその経路の**事後**成功を要求しない。次席には同じ条件での独力再参照、BtoBなら業務再使用と引き続き有効な復旧担当も必要。
4. `start = evidence_ok AND route_ok AND capacity_ok AND NOT blocked`。全条件が真なら1候補・1テストだけ開始し、起点・予測・停止条件を記録する。`false` 又は `unknown` が一つでもあれば **「持ち込める段階ではない」** とし、不足欄を `decisions` に残す。送信・設置・打診件数を成功に繰り入れない。

## 既存方針との差分

変更規程の契約・サイズ式 `E`・マージレーン・停止／解除・本人確認・版改訂・`maintenance`／`retired` の成立条件は変更しない。本書が加えるのは作業目的と差分別の予算、資源点、自然な機会を分母にした価値指標、および**任意の追加投資を許すための条件**である。ロードマップ上の有用例1件は成立例として残すが、それだけで拡大予算は開かない。保守への投資判断とrepo状態の遷移を別に記録するため、アーカイブ保守を選んでも56日条件を満たす前に監視は休止しない。親方針と競合する入力が見つかった場合は親方針を適用し、競合箇所を方針改訂要求として記録する。
