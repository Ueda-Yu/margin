# Margin — 変更単位・マージ・改善サイクル運用規程

| 項目 | 値 |
|---|---|
| 方針ID・初版 | `margin-change-policy/v1.0` |
| 対象 | 非公開の単一repo、本人1名、機能・QA・操作性／性能のBot 3系統 |
| 発効点 | 本文書を採用した `main` のSHA。以下の数値は実績ではなく初期設定 |
| 判断の優先順 | 記録を失わない → 入力を妨げない → 探せる → 再読を促す |
| 判定単位 | **リクエスト**は発生した要求、**約束**は独立して合否を示せる結果、**CL**は1本のPR。3者を別IDで追跡する |

**基本判定：同じ約束の実装・試験・証拠は1本にまとめ、別の約束は混ぜない。** CL削減の対象は重複PRと統合待ちであり、試験数ではない。`main` へのマージ、本人PCへの投入、実利用での需要確認は、それぞれ別の判定とする。

## 1. 受付と変更単位

リクエスト台帳を `docs/requests.yml`、分類規則を `policy/change-rules.yml` に置く。受付時点で未実装なら台帳の状態は `proposed` であり、完了実績にはならない。

| 条件 | 帰結 |
|---|---|
| 要求が届いた | `request_id`、出所、参照先、要望の要約、期待する結果、対象の受け入れ条件IDを発行。読書日誌から転記する場合は本文や出典そのものではなく「端末間転記で見送り」等の事象だけを残す |
| 同じ受け入れ条件ID・同じ期待結果に対する未マージPRがある | 新しい要求IDを既存PRに関連付ける。QAの失敗ケース、計測器、再現手順もそのブランチへ入れ、Bot別PRを起こさない |
| 前提なしに一方だけマージしても、他方とは別の受け入れ結果を提供できる | 別の `promise_id` にする。例：「再起動後も同一IDで読める」と「別ディレクトリへ復元できる」は別の約束 |
| 画面・DB・試験が同時にそろわないと一つの結果を示せない | 同じ `promise_id` と同じPRに置く。層別の先行マージをしない |
| 利用者への挙動を変えない整備 | 「同じ固定試料で復元を1コマンドで再現できる」等、保守担当から見た検証可能な結果を約束にする。「整理」だけなら着手不可 |
| スキーマ、migration、固定試料または期待値を変更 | 全repoで同時に開ける責任PRは1本。着手前に `contract-lock` を取得し、マージまたは取り下げで解放。他のBotは責任PRにコミットするか、契約を変更しない独立作業へ進む |
| 実装着手枠が3本、又は同じ変更予定ファイルに先行作業がある | 新規着手せず、先行PRの試験・再現・計測を支援。空き枠は「データ保全障害 → 保存・復元 → 入力 → 検索・移行 → その他」の順、同順位は受付番号昇順で割り当てる |

### サイズ判定

`main` とのmerge-baseからPR先端までの **追加行＋削除行** を `L`、変更ファイル数を `F` とする。試験・手書き試料・文書も含む。検証コマンドで完全再生成できる許可リスト内の生成物とlockfileだけは `L,F` から除き、除外前の値と再生成結果も記録する。測定不能なバイナリは生成元から一致を検証できなければブロックする。

| 条件（上から先に適用） | 判定と処置 |
|---|---|
| 約束が0個又は2個以上 | サイズにかかわらず受付へ戻す。複数の試験ケースで同じ約束の正常・異常系を示す場合は1個 |
| `L > 400` 又は `F > 12` 又は計画工数 `E > 480分` | **大きいCL**。通常マージ不可。独立して検証可能な中間結果があれば分割し、親要求と依存順を記録する |
| 大きいCLで、分離するとmigration・読書き実装・互換試料の不一致が `main` に残る | この契約変更に限り `atomic-contract` 候補。不一致を示す再現試験、旧版からの移行・復元・往復結果がそろい、`L ≤ 800, F ≤ 24, E ≤ 960分` のすべてを満たす場合だけ本人確認レーンへ。それ以外は設計を戻す |
| 大きくなく、`L ≤ 120, F ≤ 5, E ≤ 120分` のすべてを満たす | `small` |
| その他の大きくないCL | `standard` |

## 2. PR属性と見積もり

PR本文の機械可読欄に次を置く。パス・行数・日時・実行結果はCIまたはrepoイベントから取得し、手入力で軽い区分に上書きできない。パス判定は移動前後の両方に適用する。

| 属性 | 値の決定方法 |
|---|---|
| `request_ids / primary_request` | 結び付く全要求を列挙。最初に約束を発生させた受付番号が主要求。後発要求による工数の二重計上を避ける |
| `source / kind / summary / ref` | 要求ごとに、出所＝`plan / roadmap / owner-use / QA / perf / incident / maintenance`、内容＝`feature / defect / recovery / measurement / upkeep` の各1値。要約は「起点となった事象 → 期待結果」、参照先は節・Issue・失敗run・匿名化した観測IDのいずれか。出所は起票者ではなく最初の証拠で決める |
| `promise_id / acceptance_ids` | 約束1個と、それを検証する一つ以上の試験・手動判定ID。対応表には保護対象の契約と必要試験も登録 |
| `area` | `lib/db/**`、`lib/schema.sql`、`lib/transfer/**`、`tests/fixtures/**`、マージ規則・CI定義、又は永続ID・保存確定・復旧・移行・検索再構築・localhost境界の契約IDに当たれば `core`。それ以外で登録済みのUI・任意レビュー・計測器・説明文等だけなら `extension`。両方なら `core` とし `mixed=true`。未登録のパス・契約は分類表更新まで停止 |
| `owner_gate` | データの意味、対象端末、外部送信、不可逆操作、方針・ゲート定義の変更、本人PCでの受け入れ、又は `atomic-contract` なら `true`。該当する要求・契約IDのフラグの論理和。対象外のクラウド同期等は本人確認だけで着手可能にはならず、先にスコープ改訂が必要 |
| `E / effort_band` | 下式の予定総作業分。`S: ≤120`、`M: 121–240`、`L: 241–480`、`XL: >480`。待ち時間を含めない |
| `deps / actor / lock / policy` | 依存PR番号、各作業の担当、責任PR番号、適用方針の版とSHA |
| `evidence` | 候補SHA、架空試料ID、再現コマンド、期待値・実測値、CI run、未検証事項。実行前の値は `not-run` |

**工数モデル（v1.0）**：`E = 30 + 30P + 30A + 90C + 60H` 分。`P` は変更する登録済み領域の異なり数（画面／DB／転送／試料／自動試験／スクリプト／文書／CI・方針）、`A` は約束に登録された必須受け入れケース数、`C` は契約ロックの要否、`H` は本人確認の要否（各0/1）。原子例外を使う場合は `H=1` で上限を再判定する。着手時は予定パスで計算し、差分確定時は予定と実測の領域の和で再計算する。初回値も残し、見積もり誤差の検証に使う。

## 3. マージ判定と標準リードタイム

リードタイムは着手枠取得からマージまでの**暦時間**。夜間・本人待ち・CI再試行も含み、時計を止めない。次表は上から最初に一致した行を適用する。標準時間は予測であって、自動承認期限ではない。

| 条件 | 最短マージ時点 | 着手時の標準時間 |
|---|---|---:|
| 必須属性欠落、対象外要求、サイズ違反、依存未マージ、他PRのロック使用、必須試験未合格のいずれか | **停止**。理由解消後に再判定。見通しは `blocked` と元のレーン予測を併記 | 確定不能 |
| `owner_gate=true` | 共通ゲート＋対象別検証後、本人が候補SHAと確認結果を記録した時点 | `B + 24h` |
| `area=core` 又は `source` に `incident` がある | 共通ゲート＋契約別の回帰試験・障害の再現試験のうち該当するものが合格した時点 | `B + 8h` |
| `extension` かつ `small`、文書表示・説明文だけで実行経路・復旧手順・契約・期待値を変えない | **即時**＝共通ゲート成功直後に自動マージ。定例レビュー待ちなし | `B` |
| その他 | 共通ゲート＋受け入れIDに対応した統合・UI・計測試験の成功後に自動マージ | `B + 4h` |

`B` は `S=4h / M=12h / L=24h / XL=48h`。依存待ちを避けるため、未着手かつ未マージの前提がある作業は着手枠に入れない。本人確認枠は1本で、検証完了時刻順、同時ならPR番号順。着手時に先行する本人確認待ちが `q` 本なら予測に `24h × q` を加え、初回予測と最新予測を別に保存する。

- **共通ゲート**：候補と最新 `main` の統合結果に対し、属性検査・サイズ検査、既に導入済みの必須CI（lint・型・単体・移行・往復・Playwright）、対応する約束の証拠検査がすべて成功ならキューへ入る。必須runの欠落や取消は成功ではない。初期構築で未導入の試験は未導入として報告し、その試験を必要とする約束は合格にしない。
- **検証の対応**：保存なら再起動後の同一IDと失敗時の未保存表示、復旧なら別ディレクトリ復元と正本比較、移行なら旧版からの成功・失敗停止・往復、検索なら固定期待IDと索引再構築の前後一致を、変更対象の契約IDから引く。性能の納品判定なら本人PCの本番ビルド・1万件・各30回・p95 ≤ 500msを使い、10万件は後方閲覧・検索中断・完成export保全で判定する。
- **順序と失効**：マージは直列。候補SHA又は統合先が変われば、統合結果の検証を再実行し、旧候補への確認は使わない。ゲート変更PRは `main` 側の旧規則で本人が承認し、自分で緩めた規則では通さない。
- **初回適用例**：「架空の本を登録し、再起動しても同じIDで読める」は画面・DB・試験にまたがっても1約束。migrationと試料を含めば責任PRはこの1本で `core`。採用済みのデータの意味を変えなければ検証後レーン。マージ後も復旧未検証ならデモは架空データ専用で、本人の実データ投入は不可。

## 4. 監視と介入

PR作成・更新・CI終了・確認・マージ・取り下げの各イベントで判定を再計算する。時刻はUTC。必須チェック `change-policy` とマージキューを保護ブランチに結び付け、直接pushを許さない。自動化未導入時は本人が同じ表で判定結果を記名し、自動マージは無効とする。

| 観測条件 | 自動記録・帰結 |
|---|---|
| 着手、検証提出、CI開始／終了、本人確認要求／応答、マージ又は取り下げ | イベント時刻、PR・要求・約束ID、版、レーン、サイズ、予測、停止理由を台帳に追記。途中終了も工数集計に残す |
| 作業セッション終了 | 担当別に `実装 / QA / 計測 / 手戻り / 運用` と活動分を記録。本人分・Bot別稼働分・CI runner分・暦時間は別列。並行稼働分を足して経過時間とは呼ばない |
| 初回リードタイム予測の80%到達かつ未マージ | PRに残ゲート・待ち先・最新予測を1回掲示。100%超過なら `late` とし、担当は次の新規着手より詰まりの解消を優先 |
| 実作業分（本人＋Bot）が `1.5 × 初回E` 超過 | `estimate-miss`。未達の受け入れケースを記録し、サイズと約束数を再判定。超過だけでは試験を省略しない |
| 同じ候補・同じ必須試験が2回失敗 | 自動再試行を止め、QAへ失敗ケースを割当。新しい修正又は試験基盤の復旧証拠が出れば再開 |
| データ損失、正本不一致、破損時の書き込み継続を1件でも検出 | 通常マージ・実データ投入を停止し、障害要求を発行。疑わしいDBは置換せず保全。修復候補のみ検証し、別ディレクトリ復元・正本比較の合格と本人確認後に解除 |
| 新規記録があるのに最新状態の検証済み外部コピーがない | マージ可否とは別に、本人PCでのアップグレード・一括取り込みを停止。コピーの検証後に解除 |
| マージから14日以内にrevert・再オープン・回帰障害あり | 原因PRと修正要求を相互リンクし、結果を `rework` へ更新。14日未満は「回帰なし」でなく `observing` |

repoに残す証拠は対象SHA付きの架空試料結果と集計だけ。本人DB・WAL・バックアップ・実際の引用・利用日誌・個人パスを含む場合は証拠の登録を拒否し、ローカル記録への匿名IDに置き換える。

## 5. 資源と結果のフィードバック

発効時に既存コミット・PR・CI履歴を一度棚卸しする。過去の計画コミットは `planning`、実行済み試験のない結果は `unverified`、工数ログのない値は `unknown` とする。コミット間隔を工数とみなさず、欠測件数を分母とともに示す。

| 時点・条件 | 出力と判断 |
|---|---|
| 毎週月曜 00:00 UTC | 直前7日を締め、**データ損失リスク・未検証事項を先頭**に週報を生成。`area × source × lane` 別に受付・完了・取り下げ数、完了約束数、約束当たりCL数、本人分・Bot分・CI分、手戻り分、暦時間p50/p90、本人待ち時間、期限超過数、14日観測済み回帰数を掲載。完了ゼロなら比率は `N/A`、未完了は現在の滞留時間を別掲 |
| 同じ約束で複数PRが発生 | 各追加PRを `size-split / independent-prerequisite / duplicate / regression` に分類。`duplicate` が1件でもあれば翌週の受付で約束IDの重複検索を回帰試験に追加。必要な分割は削減目標に含めない |
| 4週ごとの方針レビュー | 直前28日の完了群をレーン・工数帯別に比較。件数10未満なら数値を変更せず次回へ。分位は昇順の `ceil(p × n)` 番目。欠測は除外件数を示し、当該指標の欠測率が10%を超えれば較正より先に記録経路を修正 |
| 同じ群で2回連続、実績p90が標準時間の125%超 | 待ち時間をCI待ち・本人待ち・依存待ちで比較。最大項目がCIなら重複run統合、本人なら待ち枠への投入順検査、依存なら着手前検査を次の整備要求にする。同値なら記載順。次の28日でも超過ならその群の標準時間を直近p90の時間単位切上げへ改訂提案 |
| 4週レビューで工数帯別に `実作業分 / 初回E` の中央値が2回連続で `>1.5` 又は `<0.67`（各回10件以上） | 次版候補では該当帯の工数に中央値を乗じ、15分単位で切上げる。帯の選択は補正前、サイズ・レーン判定は補正後。過去PRを再計算し、後述の試行条件へ進む |
| Weeks 5–8の週末 | 実利用の保存機会・見送り理由・自然な再参照・出典が役立った件数をローカル集計。試験検索は除外。旧ノートと新規記録を分け、機会ゼロと記録漏れを区別する。転記による見送りが2件ならUI磨き込みでなく端末経路の本人確認要求へ |
| Week 8 → Month 3 → Month 6 | Week 8で自然な参照機会がなければ「需要未検証」としてMonth 3まで展開しない。Month 3でも機会がなければ新機能・外部展開は凍結、旧ノートだけが役立てばアーカイブ保守へ。Month 6で本人利用のみなら単独保守、他者が独力で再参照できた場合だけ同条件の次の1席を候補にする |

## 6. 方針の版と終了条件

| 条件 | 方針の状態遷移 |
|---|---|
| 4週レビューで複数の改訂候補がある | 安全不具合 → 記録欠測 → 待ち時間 → 工数較正の順に1件だけを次の方針PRへ。変更理由・対象群・旧値・新値・直近28日の再判定差分を添える |
| 数値又は分類規則の変更が承認された | minor版を上げ、旧版と適用開始SHAを保存。新規着手分だけで28日試行する。安全上の停止規則の強化だけは開いているPRにも即時適用 |
| 試行終了 | 対象群が新旧各10件以上で、対象指標（待ち時間なら待ちp90、工数なら `abs(実績/見積−1)` の中央値）が低下し、14日観測済みの回帰率が増えず、対象群の本人作業分／完了約束数も増えなければ採用。最終PRの14日観測終了までは判定保留。件数不足なら28日だけ延長し、なお不足又は条件不成立なら旧版へ戻す。保全障害は試行終了を待たず停止 |
| Week 4終了、Week 8終了、Month 3、Month 6 | 定例較正とは別に、本人が単一ユーザー・ローカル運用・Bot構成の前提を確認。公開運用、複数書き込み主体、本人以外への承認委譲のいずれかが決まれば現版を拡張流用せず、権限と復旧責任を定めた次のmajor版が発効するまで該当変更を停止 |
| 未完了要求・開いているPRがともに0件で、56日間着手なし | 状態を `maintenance` にし、空の週報と数値較正を休止。利用中はバックアップ確認・月次別ディレクトリ復元を継続。次の着手時に現版・保護設定・最終復元結果を確認できれば再開 |
| repoを読み取り専用化し、最終の検証済み外部バックアップ・可読Markdown・別ディレクトリ復元結果がそろった | 状態を `retired` とし、PR監視・改善サイクルを終了。版、判定履歴、最終SHAは削除しない。再開時は新しい発効点を記録し、休止期間をリードタイム実績に混ぜない |
